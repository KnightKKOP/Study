# 功能清单

ForgeMesh 要补的功能，按求职价值排序。编号对应上游 [Mekoforge/ForgeMesh](https://github.com/Mekoforge/ForgeMesh) 的 `docs/architecture/roadmap.md`。

现状：网关只有按服务名的流式路由，限流是单机内存里按租户的令牌桶，流式转发不解析 token 用量，每个服务只有一个实例。所以 MaaS 接入层和推理感知路由都是实打实的新功能，也正好对应你在工作中参与过的模型网关设计。

## 必做

| 功能 | 路线图编号 | 为什么值得做 | 验收标准 |
|---|---|---|---|
| 发布 v1.1.0 与文档整理 | 4.0 | 现在没有任何版本标签；README 的功能概览还写着 v1.0.0；`architecture.md` 里有指向本机路径的残留。 | 打出 v1.1.0 标签，发布记录列出破坏性变更与迁移方式。 |
| 真实 GPU 验证与压测报告 | 4.2-E | 证明不是纸面项目；面试要你自己测出来的数字。 | `vllm-process` 在 GPU 上跑通创建、`Ready`、对话、更新、实例丢失、删除；有 TTFT、TPOT、吞吐和网关开销的数据。 |
| 模型抽象与 OpenAI 兼容接口 | 4.3-B | MaaS 的门面，直接对口岗位；现在网关只有按服务名的流式路由。 | OpenAI 官方 SDK 只改 `base_url` 和 key，就能流式与非流式调用。 |
| RPM / TPM 配额 | 4.3-C | 模型网关的核心难点：流式响应的 token 数事先未知，需要预扣与结算；多个网关副本要共享计数。现在只有单机按租户的令牌桶。 | 超出 TPM 返回 429 与 `Retry-After`。 |
| token 计量 | 4.3-D | 计费的基础，考察一致性与幂等；现在流式转发不解析用量。 | 计量记录与响应中的 usage 一致，重试不重复计。 |
| 多副本与应用层健康检查 | 4.2-A、4.2-C | 推理感知路由的前提；现在每个服务只有一个实例，核对实例只看进程是否还在。 | 3 个副本被杀掉一个时服务不中断。 |
| 推理实例指标与推理感知路由 | 4.4-A、4.4-B | 当前 AI Infra 最热的方向（Gateway API Inference Extension、llm-d、Kthena router），而且能拿出量化对比。 | 在共享前缀负载下，有与轮询对比的 TTFT P99 和吞吐数据。 |
| 智能诊断 Agent | 新增（需要 ADR） | 把 Agent 方向和你在工作中做过的一键定位经验并进同一个项目，是别人没有的差异化。 | 故障注入评测集上有定位准确率与失败案例分析。 |

## 选做

| 功能 | 路线图编号 | 为什么值得做 | 验收标准 |
|---|---|---|---|
| Kthena 或 KServe 后端 | 4.1-B | 投云原生 AI 平台岗位时加分；在 kind 上用 CPU 小模型就能验证，不花 GPU 的钱。 | kind 上跑通创建、`Ready`、对话、更新与删除。 |
| 滚动更新 | 4.2-B | 经典问题，难度适中，和多副本放在一起讲。 | 更新期间的请求全部成功。 |
| OTLP 追踪 | 4.1-E | 改动小，补齐可观测性，和你的运维经验呼应。 | 在 Jaeger 里看到跨网关与控制平面的完整 trace。 |
| 自动扩缩 | 4.4-C | 和推理感知路由放在一起讲很完整。 | 按排队请求数在 min 与 max 之间扩缩，有冷却时间。 |
| Node Agent 的 gRPC 与 mTLS | 4.1-A | 分布式系统的深度，但工作量大。 | 两个进程经真实网络联调，断网恢复后同一个任务不重复执行。 |

## 暂缓

PostgreSQL 与 leader 选举（5.1）、插件进程隔离（5.2）、LoRA 与模型目录（5.3）、PD 分离（5.4）、多机分布式推理（4.4-D）。这些要么需要多机多卡，要么工作量大但面试回报低，拿到 offer 之后再按兴趣做。
